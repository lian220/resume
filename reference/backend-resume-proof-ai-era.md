## 한 줄 결론

> **백엔드 실력은 “믿을 수 있는 증거로 바꾼 기록”이다.**

AI가 코드를 더 빨리 쓰게 해줘도, 이력서에서 평가되는 중심은 크게 바뀌지 않았다. 중요한 것은 “AI를 썼다”가 아니라 **내가 어떤 백엔드 문제를 정의했고, 어떤 기술로 해결했으며, 그 결과를 어떤 수치와 근거로 검증했는가**다.

---

## 핵심 공식

> **백엔드 실력 증명 = 핵심 기술 × 문제 소재 × 검증 증거**

이 셋 중 하나만 있어서는 약하다.

- 핵심 기술만 있음 → 기술 스택 나열에 그침
- 문제 소재만 있음 → 실제 해결 역량이 불명확함
- 검증 증거만 있음 → 왜 중요한 문제였는지 맥락이 약함

따라서 이력서 문장은 항상 아래 질문에 답해야 한다.

1. **핵심 기술**: 어떤 백엔드 기술을 다뤘는가?
2. **문제 소재**: 그 기술이 왜 필요한 문제였는가?
3. **검증 증거**: 해결 결과를 어떤 수치/로그/재현 근거로 확인했는가?

---

## 1. 핵심 기술 — 무작정 스택을 늘리지 않는다

신입/주니어 Java·Spring 백엔드 기준으로는 Kafka, MSA, Kubernetes 같은 큰 스택을 무리하게 넣기보다, 아래 기본 스택에서 문제 해결과 검증을 만드는 것이 더 안전하고 설득력 있다.

- Spring Boot
- JPA
- 인덱스
- 트랜잭션
- 락
- 쿼리 최적화
- Redis
- 성능 측정/수치화

핵심은 “대단한 기술을 썼다”가 아니라, **지원하는 팀이 실제로 풀고 싶은 문제와 연결되는 기술을 제대로 설명할 수 있느냐**다.

### 주의

- Kafka/MSA는 신입 이력서에서 공격 지점이 커질 수 있다.
- 기술을 메인 소재로 세우면 면접에서 운영 경험, 장애 대응, 내부 원리까지 질문받을 가능성이 높다.
- 모르면 “써봤다”보다 위험하다. 기술은 자신 있게 설명 가능한 범위에서 선택한다.

---

## 2. 문제 소재 — 이력서의 차별점

이 영상에서 가장 강하게 강조한 부분은 **문제 소재의 신선도**다.

예전에는 `JPA N+1 해결`만으로도 어느 정도 어필이 됐지만, 이제는 너무 흔해져서 이력서 메인 소재로는 약하다. 면접관이 수많은 이력서에서 같은 소재를 보기 때문에 “이 사람이 진짜 문제를 고민했나?”가 잘 드러나지 않는다.

좋은 문제 소재는 다음 조건을 가진다.

- 단순 구현이 아니라 병목/장애/운영/품질 이슈와 연결된다.
- 비즈니스 요구사항 때문에 기술 선택이 필요해진다.
- 왜 이 문제를 풀었는지 설명 가능하다.
- 면접관이 질문하고 싶어지는 구체성이 있다.

### 좋은 소재 예시

- 결제 상태 조회 API에서 반복 DB 조회로 QPS·CPU가 증가하는 문제
- 실패 메시지의 무제한 재시도로 장애가 커지는 문제
- DLQ와 백오프 전략을 통한 재시도 폭주 제어
- AI 생성 코드 증가로 코드 리뷰 부담이 커지는 문제
- CI 정적 검사로 컨벤션/품질 위반을 자동 검출하는 문제
- 특정 API 병목을 실행 계획·부하 테스트로 확인하고 개선한 문제

---

## 3. 검증 증거 — 숫자와 재현 근거로 끝낸다

“개선했다”는 표현만으로는 부족하다. 반드시 Before/After와 측정 방식이 있어야 한다.

사용 가능한 증거:

- TPS
- QPS
- P95/P99 latency
- 평균/최대 응답 시간
- CPU/메모리 사용률
- DB 조회량
- 쿼리 개수
- 실행 계획 비교
- 에러율
- 재시도 횟수
- DLQ 건수
- 장애 복구 시간
- CI 차단 건수
- 코드 리뷰 지적 감소량

### 약한 문장

> JPA N+1 문제를 해결했습니다.

### 강한 문장

> 결제 상태 조회 API에서 반복 DB 조회로 QPS와 DB CPU가 증가하는 문제를 발견했고, Redis 캐시와 TTL 정책을 적용해 P95 응답 시간과 DB 조회량을 각각 측정·비교했다.

실제 이력서에서는 `[확인 필요]` 수치를 채운다.

> 결제 상태 조회 API에서 반복 DB 조회로 P95 응답 시간이 `[확인 필요]ms`까지 증가하는 문제를 발견했고, Redis 캐시와 TTL 정책을 적용해 P95를 `[확인 필요]ms`로 낮추고 DB 조회량을 `[확인 필요]%` 줄였다.

## AI 시대의 핵심 관점

AI는 세 칸을 대체하지 않는다.

> **AI는 핵심 기술·문제 소재·검증 증거를 대신 만들어주는 것이 아니라, 실험과 구현의 속도를 높이는 가속 도구다.**

따라서 이력서에서 AI를 메인으로 세우기보다, 다음처럼 사용하는 것이 좋다.

- 문제 가설을 빠르게 확장한다.
- 테스트 코드와 부하 테스트 스크립트를 빠르게 만든다.
- 측정 결과를 정리하고 문서화한다.
- CI/CD, 코드 리뷰, 태스크 관리, 모니터링 흐름을 보조한다.
- 단, 핵심 기술과 설계 판단은 본인이 설명할 수 있어야 한다.

### 신입/주니어 주의

처음부터 AI에게 전부 맡기면 학습 능력이 떨어질 수 있다. 최소한 이력서에 적을 핵심 기술은 직접 손으로 구현하고, 에러를 보고, 로그를 읽고, 수치를 측정해본 뒤 AI로 확장하는 편이 안전하다.

면접은 결국 본인이 설명해야 한다. AI가 만든 코드를 이해하지 못하면 이력서 소재가 아니라 리스크가 된다.

## PAR 구조로 바꾸기

이 영상의 공식은 기존 `PAR` 작성법과 잘 맞는다.

| 구조 | 이번 영상 기준 | 이력서 질문 |
|---|---|---|
| P — Problem | 문제 소재 | 왜 이 문제가 중요했나? |
| A — Analyze/Action | 핵심 기술·해결 과정 | 어떤 대안을 검토했고 왜 이 방식을 택했나? |
| R — Result | 검증 증거 | 무엇이 얼마나 개선됐나? |

이력서에는 최소 2~3개의 PAR 킬링 문장이 있어야 한다.

### 템플릿

```md
- [Problem] `{비즈니스/운영 상황}`에서 `{구체 문제}`가 발생해 `{사용자/운영/비용 영향}`이 있었다.
- [Analyze/Action] `{대안 A/B}`를 비교했고, `{선택 근거}` 때문에 `{핵심 기술}`을 적용했다.
- [Result] `{측정 방식}` 기준 `{Before}` → `{After}`로 개선했고, 남은 한계는 `{한계/후속 과제}`로 정리했다.
```

## 이력서 메인 소재로 약한 것

아래는 의미가 없다는 뜻이 아니라, **메인 요리보다는 서브/반찬에 가깝다**는 의미다.

- 단순 CRUD 프로젝트
- JPA N+1 해결만 강조
- 단순 커넥션 풀 조정
- 서버 스케일업/장비 증설
- 단순 리팩토링
- 클린코드·DDD·TDD 자체를 메인 성과로 쓰는 것
- “AI로 기능을 빠르게 만들었다” 수준의 설명
- Kafka/MSA를 이유 없이 넣은 프로젝트

특히 클린코드, DDD, TDD는 중요하지만 **학습과 코드 통제의 영역**에 가깝다. 이력서 메인 소재로 삼기보다, 문제 해결을 뒷받침하는 설계 근거·품질 기준으로 녹이는 것이 좋다.

## 사이드 프로젝트 전략

회사에서 좋은 문제 해결 소재가 나오지 않으면 사이드 프로젝트를 해야 한다.

특히 다음 경우:

- 회사 기술 스택이 지원하려는 백엔드 포지션과 다르다.
- 실무에서 성능 측정/트러블슈팅 기회가 없다.
- 신규 기능 개발만 반복하고 있다.
- 이력서에 쓸 수 있는 수치와 증거가 없다.

사이드 프로젝트는 “서비스 하나 만들었다”가 아니라 처음부터 이력서 소재를 의도하고 설계한다.

### 설계 질문

- 어떤 도메인 요구사항을 가정할 것인가?
- 어떤 트래픽/부하/운영 문제를 만들 것인가?
- 어떤 핵심 기술이 반드시 필요해지는가?
- 어떤 지표를 Before/After로 측정할 것인가?
- 면접에서 어떤 질문을 받을 수 있고, 어디까지 설명 가능한가?

---

## 정파 vs 사파 프레임

영상에서는 취업 전략을 설명하기 위해 `정파/사파` 비유를 사용했다.

### 정파

- 알고리즘, CS, OS, DB 내부구조, JVM/GC 같은 근본기 중심
- 네이버/카카오 공채식 준비와 가까움
- 코딩 테스트, CS, 학벌, 연구, 대회 성과가 강점

### 사파

- 서비스 기업/스타트업/현업 문제 해결 중심
- 비즈니스 요구사항, 트래픽, 병목, 장애, 운영 경험 강조
- 이력서에서 문제 해결 사례와 수치가 중요

단, 사파가 기초 공부를 안 해도 된다는 뜻은 아니다. 기초는 베이스라인이고, 합격을 결정하는 차별점은 **문제 해결 증명**이라는 의미다.

## 내 이력서 적용 메모

현재 이력서 저장소 기준으로는 아래 문서들과 연결된다.

- `reference/par-writing-guide.md` — PAR 구조 작성법
- `reference/portfolio-topic-strategy.md` — AI 시대 포트폴리오 주제 선정
- `reference/portfolio-apply-check.md` — 실제 프로젝트 적용 체크
- `interview/ai-trend-notes.md` — AI 시대 기술면접 대응

### 보강 방향

1. `resume-data.mjs`의 각 성과 항목을 **핵심 기술 × 문제 소재 × 검증 증거** 기준으로 재점검한다.
2. `[확인 필요]` 수치가 남아 있는 Result를 우선 채운다.
3. STAR/PAAR 문장 중 Action만 나열된 항목은 Problem과 Analyze를 앞으로 끌어올린다.
4. Alpha Foundry 같은 사이드 프로젝트는 “AI 퀀트 플랫폼을 만들었다”보다 **백엔드 병목/검증 소재**를 메인으로 재정렬한다.
5. AI 활용 경험은 메인 기술보다 **개발 라이프사이클 가속·검증 보조**로 표현한다.

### 내 문장 점검 체크리스트

- [ ] 이 문장에 핵심 기술이 명확히 보이는가?
- [ ] 이 기술이 필요한 문제 소재가 있는가?
- [ ] 문제 소재가 흔한 소재에 머무르지 않는가?
- [ ] Before/After 수치가 있는가?
- [ ] 측정 방식이나 재현 명령을 설명할 수 있는가?
- [ ] 남은 한계나 후속 과제를 말할 수 있는가?
- [ ] AI가 했다가 아니라, 내가 판단하고 검증했다는 구조인가?
